## Problem Statement

remobi 的核心弱网问题不是终端帧率下降，而是用户在 Android 或 iOS 上离开几十分钟、切换网络或锁屏返回后，无法同时确认三件事：屏幕是否为最新状态、语音长草稿是否安全、整条指令是否已被服务端接收。当前刷新式重连、内存草稿和无确认输入会分别破坏这三种信任。

真实使用方式：用户布置任务后只观察开头，随后离开；再次介入时结合终端上下文，通过语音输入大段指令。通知可以减少主动查看，但不是本轮弱网主链路。

## What Makes This Cool

连接可以消失，但用户的上下文不能变得含糊。remobi 在弱网下始终回答三个问题：我看到的是不是最新画面、我的草稿还在不在、这条长指令到底收到没有。

## Constraints

- 个人自用、单机单用户，risk-tier 为 personal。
- 保留现有浏览器触控、语音 composer 和 Herdr WebUI；Mosh 只作为紧急终端备用。
- 复用服务端 headless terminal mirror 与 attach snapshot，不移植 Mosh 协议。
- 不新增数据库、通用离线队列、Agent inbox、多设备同步或多租户设计。
- 普通逐键终端输入保持现状；确认协议只覆盖用户显式提交的整条语音指令。
- 自动回车与最终文本组成同一个原子 action；不能继续按“文本一次、`\r` 一次”发送。
- “已接收”只表示 remobi 服务端成功调用当前 PTY 的 `write(data)`，不表示操作系统已落盘或 Herdr 已执行完成。

## Premises

1. 弱网体验的首要目标是恢复可信、草稿不丢、整条指令不重不漏。
2. 浏览器通知是后续可选增强，不属于本轮核心闭环。
3. 旧画面可以暂时保留，但必须明确标记为过期或同步中；只有当前连接收到服务端 snapshot 后才能标记为已同步。
4. 语音草稿与唯一待确认 action 必须一起跨刷新、`pagehide/pageshow` 和断线保留；只有用户明确清空/放弃，或对应指令被确认接收后才能删除。
5. 对整条语音提交使用稳定 action ID；最终 `data` 已包含可选自动回车。确认丢失后的重送沿用同一 ID，当前 PTY session 内有界去重。
6. 跨服务端进程崩溃的严格 exactly-once 不解决；服务重启也会重建其持有的 PTY session，这不是本轮要伪装保证的能力。

## Cross-Model Perspective

独立 Codex 将目标概括为“弱网驾驶舱”：不隐藏断线，而是显式呈现离线、同步中、已同步和待确认。它建议按草稿保护、原地重连、画面新鲜度、整条指令确认的顺序实现，并明确反对移植 Mosh 协议或为跨进程 exactly-once 建持久化日志。

## Approaches Considered

- **A：草稿与诚实状态。** 改动最小，但保留刷新重连且无法证明指令送达，未闭合核心目标。
- **B：三段弱网闭环。** 原地重连与新 snapshot、草稿持久化、整条语音提交的 action ID/accepted/会话内去重。用户已选择。
- **C：完整离线与重放。** IndexedDB outbox、统一事件重放和跨重启日志；因个人工具没有对应规模且误重放终端命令风险更高而排除。

## Recommended Approach

采用 B，但不创建通用连接平台。

### 1. 恢复可信

不新增通用 `ConnectionManager` 类。`client-entry` 继续拥有连接，在同一模块内收口 `connect()`、当前 socket、连接代次、snapshot 缓冲和重连计时器；`reconnect` UI 只展示状态并触发“立即重试/重新认证”。

```text
          close / offline / heartbeat timeout
 synced ----------------------------------------> disconnected
    ^                                                 |
    | current epoch snapshot                          | visible: 立即尝试
    |                                                 | 后续 1s,2s,4s,8s,15s
 syncing <---------------- socket open <--------- reconnecting
    |
    +-- 连续 3 次同步前失败 --> 仍重试，但显示“可能需要重新认证”+ 手动刷新

 hidden/pagehide：立即把画面标为可能过期、停止后台计时器并主动关闭当前 socket；pageshow/visible 时无条件创建新连接，即使旧 socket 先前仍显示 OPEN。online 只作为提前重试提示，不能证明服务可达。
 15s 是单次退避上限，不设总次数上限；页面可见且仍离线时每 15s 尝试一次。
```

- 每次 `connect()` 递增 epoch。open 时进入 `syncing`，重置该 epoch 的 `snapshotLoaded` 与 output buffer，并启动 10 秒 snapshot deadline；只有当前 epoch 的 snapshot 能取消 deadline 并进入 `synced`。deadline 到期主动关闭 socket，按一次“同步前失败”处理；旧 socket 的 open/message/error/close/pong 全部忽略。
- 进入 `hidden` 或 `pagehide` 时立即使当前 `synced` 失效并关闭 socket；从 `visible` 或 `pageshow` 返回时始终建立新 epoch 并重新获取完整 snapshot。不能因为旧 socket 仍为 OPEN 就沿用休眠前的“已同步”判断。
- 服务端给每个 PTY output 分配 session 内单调 `seq`，output 消息携带该值。snapshot 通过“读取当前 pending mirror promise → await → 确认 promise 未被新 output 替换”的稳定循环取得 `{data, outputWatermark}`；同步返回前的序列化在同一事件循环 turn 内完成，保证 snapshot 包含 `seq <= outputWatermark` 的输出。客户端收到 snapshot 后丢弃缓存中 `seq <= outputWatermark` 的 output，只按序应用更大的 seq，避免 snapshot 已包含的数据被重放两次。
- 当前 epoch 在 snapshot 前缓存的 output 按 UTF-8 字节计数，最多 1 MiB。超过上限时立即关闭该 socket，显示“输出过快，等待稳定后重新同步”，并按正常退避重试；不能让持续刷屏在 10 秒 snapshot deadline 内无界占用手机内存。
- 断线后保留旧终端画面并覆盖“内容可能过期”；`connected` 只表示 socket OPEN，不能作为允许提交的门槛，composer action 仅在 `synced` 时发送。
- heartbeat 协议扩为 `{ type: "ping", id }` / `{ type: "pong", id }`。同一时间只允许一个在途 ping：进入 `synced` 后发送一次并启动 15 秒 deadline；收到当前 epoch 且 ID 匹配的 pong 后清除 deadline，再等待 10 秒发送下一次。错误 ID 或迟到 pong 不能续命；deadline 到期关闭当前 socket 并进入 `disconnected`。heartbeat 只证明链路存活，snapshot 才证明内容已收敛。
- “同步前失败”统一指 socket 在当前 epoch 收到 snapshot 前 error/close，或 snapshot deadline 到期。Cloudflare Access 过期无法可靠地和网络失败区分；连续 3 次同步前失败后显示“连接失败，可能需要重新认证”，保留草稿和 pending action；用户点“重新认证”才执行整页刷新。
- 不引入协议版本协商。新客户端若收到缺少 `sessionId` 或 `outputWatermark` 的旧 snapshot，保留草稿与 pending、禁用原子提交，并显示“服务端版本不匹配，请刷新”；新服务端继续接受旧客户端的普通 input。这个字段存在性守卫覆盖单人部署的升级与回滚，不扩成通用兼容平台。
- `disconnected/reconnecting/syncing` 均禁止普通 input：不排队、不重放，并给出“未发送，连接尚未同步”提示。resize 在非 synced 期间只覆盖保存最后一个值，synced 后发送一次；唯一 pending composer action 只在 sessionId 匹配的新 epoch `synced` 后自动重送。
- `client-entry` 是连接状态的唯一事实源；任一时刻最多存在一个活动 socket、一个重连 timer 和一个在途 ping。`online/pageshow/visibilitychange` 事件只合并成一次立即尝试，不能并发创建 socket。退避和连续同步前失败计数只在完整 snapshot 应用成功后清零，socket OPEN 本身不算恢复成功。`reconnect.ts` 只渲染状态和转发用户操作，不维护第二份 `disconnected` 布尔值。
- 现有 `XTerminal.isConnected()` / `onConnectionChange()` 的布尔语义从“socket OPEN”收紧为“当前 epoch 已完成 snapshot 并处于 synced”；另外暴露只读连接状态给 `reconnect.ts` 渲染四种文案。composer 与 reconnect UI 是这份状态的两个真实消费者，因此扩展现有桥接契约是必要边界，不新增通用连接类。

### 2. 草稿不丢

- localStorage key 固定为 `remobi:composer:v1:${basePath}`；origin 已由浏览器隔离，base path 区分 `/` 与 `/remobi/`。
- 单条 schema：`{ version: 1, draft, pending }`，其中 `pending` 为 `null` 或 `{ id, sessionId, sourceText, data, status, reason? }`；`status` 为 `pending | unknown | rejected`，`data` 是 hook、sanitize 和可选自动回车全部完成后的最终 PTY 输入。
- composer 每次变化后同步写入；初始化、刷新和 `pageshow` 时恢复。JSON 损坏或 schema 不匹配时不自动覆盖原值，显示“草稿恢复失败”；写入抛错或配额失败时显示“草稿未受保护”。
- 获取 `window.localStorage`、读取 key、解析和写入任何一步抛出 `SecurityError` / `QuotaExceededError` 都走同一条可见失败路径；内存中的 textarea 内容继续保留。单条最终 action 沿用现有 256 KiB 输入上限，普通长草稿不引入 IndexedDB。
- 用户点击提交后先捕获 `sourceText`，完成 hook/sanitize；若可发送正文为空，则不附加 `\r`、不生成 action，并显示“没有可发送的文本”。否则生成 `crypto.randomUUID()`，持久化完整 pending，再发送。hook 取消时不生成 action。
- pending 存在时禁用再次提交，但 textarea 仍可编辑且继续持久化。accepted 到达后无条件删除匹配 pending；只有当前 draft 仍等于 `sourceText` 才同时清空 draft。用户已经编辑出的新文本继续保存，且发送按钮随 pending 删除立即恢复。
- 清理 pending 只有三条路径：匹配 accepted；用户明确“放弃本次待确认提交”；用户清空全部草稿并二次确认待确认 action 也一并放弃。

### 3. 提交不重不漏

```text
draft --点击提交--> pending(已持久化) --同 sessionId 且 synced--> sent
                         ^                         |
                         | 新 epoch 自动重送一次   | accepted(id)
                         |                         v
                    unknown <--- 15s 超时 ------ accepted/清理
                         |
                         +-- 用户“重试”沿用同一 ID
                         +-- 用户“放弃”只清本地 pending，不声称服务端未写入

 sent -- input-rejected --> rejected（保留 pending 与 reason，停止自动重送）
 新 snapshot 的 sessionId 不同 --> unknown（禁止自动重送，等待用户判断）
```

- 每个 SharedTerminalSession 启动时生成 `sessionId = crypto.randomUUID()`，随 snapshot 发送。创建 pending 时保存当时的 sessionId；重连 snapshot 的 sessionId 不同，说明服务/PTY session 已变，旧 action 只能标记 unknown 并等待用户决定，禁止自动重送。
- composer action：`{ type: "input-action", id, data }`；成功响应：`{ type: "input-accepted", id }`；ID 冲突、PTY 不可用或 `write` 抛错响应：`{ type: "input-rejected", id, reason }`，reason 是固定枚举 `id-conflict | pty-write-failed | session-unavailable`。旧客户端的 `{ type: "input", data }` 继续作为无确认的逐键输入；独立消息类型避免用可选 `id` 制造模糊协议分支。
- 无法可靠提取 action ID 的畸形 JSON、未知消息类型、缺失/错误字段或超出大小限制，沿用现有协议违规策略关闭 WebSocket，不伪造 rejected；只有结构合法且已取得 ID 的 action 才能收到 accepted/rejected。session 在解析后已不可用时，先回 `input-rejected(session-unavailable)` 再关闭连接。
- action ID 使用 `crypto.randomUUID()` 并随 pending 持久化。相同 ID、相同 data：不再次 `pty.write`，只重发 accepted；相同 ID、不同 data：`input-rejected(id-conflict)`，不写 PTY。
- 服务端只在 `pty.write(data)` 同步返回成功后，先把 `{id,data}` 写入去重 Map，再发送 accepted；这保证 accepted 丢失时重送能命中去重。仅在这一次调用边界 catch 同步异常并转换为 rejected(`pty-write-failed`)；异常时不写 Map，不宣称接收成功。
- 现有 mirror write 链上的静默 `.catch(() => {})` 不能继续作为 snapshot 可信链路的一部分。mirror write 一旦失败，记录粘性 session 错误、向当前客户端发送不含终端正文的 error 并关闭连接；后续 attach 直接失败，要求重启 remobi。关闭中的 `raw.send()` 竞态仍可忽略，因为客户端 pending 会进入 unknown 并在新连接重试，这不是吞掉业务结果。
- 当前连接发送后 15 秒没有 accepted/rejected，UI 进入“结果未知”。同一连接不自动盲重试；每个后续 synced epoch 最多自动重送一次，用户也可手动用同一 ID 重试。
- rejected 保存 reason、停止自动重送，并显示“未接收：{reason 对应文案}”；用户可放弃，或修正草稿后放弃旧 action 并生成新 ID。`pty-write-failed` 允许用户用原 ID 手动重试，其他 reason 必须先放弃旧 action。
- SharedTerminalSession 用容量 128 的 FIFO Map 保存 `{id,data}`，生命周期与该 PTY session 相同；淘汰最旧记录，不设数据库或 TTL。在支持的单用户、单 pending 流程中，pending 未确认时不能创建后续 action，因此其 ID 不会被本客户端的后续 action 淘汰。服务重启由 sessionId 变化阻止自动重送。
- 发送按钮在 pending/unknown 存在时禁用，避免双击和第二个并发 action；关闭 composer 不删除 pending。
- `runBeforeSendData` 仍只在用户首次点击提交时运行；await 返回后重新检查 composer generation 与 `synced` 状态，再构造最终 `data`。首次 `socket.send(input-action)` 返回后运行一次 `runAfterSendData`，其 `data` 包含可选 `\r`；重连自动重送和服务端重复 accepted 不重复触发业务 hook。

## NOT in Scope

- Web Push、浏览器通知和 Herdr blocked 状态监听。
- Mosh 协议集成或替换 remobi WebUI。
- IndexedDB outbox、通用消息总线、跨服务重启 exactly-once。
- 普通键盘逐键确认、离线终端输入、多设备草稿同步。
- 多标签页同时编辑同一个 composer；同 origin 下最后一次 localStorage 写入覆盖前值，个人使用时只保留一个活动 composer 页面。

## Validation Unknowns

- 真机上从 Wi-Fi 切蜂窝、锁屏再恢复时，`online`、`pageshow`、`visibilitychange` 和 WebSocket close 的实际触发顺序，需要先录一次 Android 与 iOS 基线。
- 当前 Cloudflare Access 会话过期时浏览器可见的 close/error 形态，需要真实入口验证；产品行为已经锁定为连续失败后提示手动刷新认证，不承诺自动识别原因。

## Success Criteria

1. Android 与 iOS 上输入多行长草稿后刷新、切后台再回来，文本逐字恢复。
2. 断网时界面不再显示“已同步”；网络恢复后，只有当前连接应用服务端 snapshot 才恢复该状态。
3. 弱网期间终端继续输出，恢复后浏览器内容收敛到服务端 mirror 的最新 snapshot。
4. 同一 SharedTerminalSession 且 ID 仍在去重 Map 时，服务端已调用 PTY write 但 accepted 丢失，客户端以同一 ID 重送不会产生第二次 PTY 输入；sessionId 改变时不自动重送。
5. composer 提交状态只出现“未发送、待确认、已接收、结果未知/失败”，不声称 Herdr 已执行。
6. 既有触控、普通键盘输入、语音识别和单连接流畅网络体验不回归。
7. 普通 input 在重连期间不会进入重放队列；resize 只应用断线期间最后一个值。
8. `autoEnter` 开启时文本与 `\r` 作为同一 action 只写入 PTY 一次。

| 单测 | 旧 epoch 的迟到 accepted/rejected、unknown 后迟到 accepted | 旧 socket 事件不能改变当前状态；当前 session+ID 的迟到 accepted 仍能清理 pending |
| 单测 | before/after hook 与自动重送 | await before 后重新检查 generation/synced；after 只在首次发送运行一次且拿到含可选回车的最终 data |
| 单测 | rejected reason 与 write throw | 状态为 rejected；reason 可见；throw 时不写去重 Map |
| 协议 | 相同 ID 相同/不同 data | 相同 data 只 ack；不同 data reject；PTY 不重复写 |
| 协议 | `autoEnter` | 最终 `data` 包含一次 `\r`，accepted 对整个 action 生效 |
| 集成 | PTY write 成功但 accepted 丢失 | 新 epoch 同 ID 重送，PTY 仍只收到一次 data |
| 集成 | snapshot 与 output 乱序/重复覆盖 | snapshot 携带 watermark；客户端丢弃 `seq <= watermark` 的缓存 output，最终画面等于 mirror 且无重复字符 |
| 集成 | snapshot 前输出缓存超过 1 MiB、mirror write 失败 | 前者关闭并退避重连且提示输出过快；后者使 session fail-loud，禁止再宣称 synced |
| e2e | 离线期间普通 input 与 resize | input 显示未发送且不重放；仅最后 resize 生效 |
| e2e | socket OPEN 但仍 syncing | 普通 input 与 composer action 均不发送；snapshot 后才放行 |
| 集成 | FIFO 淘汰与 session 重启 | 淘汰顺序符合容量；新 sessionId 下旧 pending 变 unknown 且不自动重送 |
| 协议 | malformed action / session unavailable | 无可靠 ID 的帧关闭连接；合法 ID 且 session 不可用时 reject 后关闭 |
| 兼容 | 新客户端连接旧服务端 | 缺少 snapshot 必需字段时保留草稿/pending，禁用原子提交并提示刷新；旧客户端普通 input 仍被新服务端接受 |

## CEO Scope Reduction Review

### What already exists

- 服务端已经有 `SharedTerminalSession`、headless terminal mirror 和客户端 attach snapshot，弱网恢复无需另建会话存储。
- 客户端已经有 WebSocket、语音 composer、Cloudflare Tunnel + Access 真实入口和 Android/iOS 浏览器入口。
- 当前真正缺少的是三个很薄的契约：snapshot 证明画面新鲜、localStorage 保护长草稿、单条 composer action 有接收确认。
- 当前 `location.reload()` 式恢复、内存草稿和普通 input 队列不能提供这三个契约，应替换或收窄，而不是在外面再包一层平台。

### Dream State Delta

完成后，用户在手机离开几十分钟、切网或锁屏返回时，可以立即分辨画面是过期、同步中还是已同步；未提交的长语音文本跨刷新保留；提交后得到“待确认、已接收、结果未知或失败”的诚实状态。仍然不提供后台通知、Mosh 风格全终端漫游、跨进程 exactly-once 或多设备同步——这些都不是本轮弱网信任闭环所需。

### Minimum Architecture

```text
Android / iOS 浏览器
  ├─ terminal 画面：旧画面 + 新鲜度状态
  ├─ voice composer：draft + 唯一 pending action
  └─ WebSocket：epoch / heartbeat / reconnect
             │
             ▼
Cloudflare Access + Tunnel（不改）
             │
             ▼
remobi /ws
  ├─ 协议解析与字段边界
  └─ SharedTerminalSession
       ├─ mirror + output seq + snapshot watermark
       ├─ sessionId
       └─ 128 条 action 去重 Map
             │
             ▼
同一 node-pty / Herdr
```

没有新增服务、数据库、依赖、后台 worker、功能开关或通用连接抽象。

### User Flow

```text
打开/返回页面
  │
  ├─ disconnected / reconnecting / syncing
  │    ├─ 旧画面明确标“可能过期”
  │    ├─ 普通按键不发送、不重放
  │    └─ 草稿继续本地保存
  │
  └─ 收到当前 epoch snapshot
       ▼
     synced
       │
       ├─ 继续阅读最新终端
       └─ 语音输入长文本 → 清洗 → 先持久化 pending → 单 action 发送
                                          │
                        accepted ──────────┼──→ 清 pending；未改过的 draft 才清空
                        15s 无结果 ────────┼──→ unknown；同 session 新 epoch 最多重送一次
                        sessionId 改变 ────└──→ unknown；不自动重送，由用户判断
```

### Data and State Boundaries

```text
PTY output(seq)
  → mirror write 完成
  → snapshot(data, outputWatermark)
  → 客户端丢弃 seq <= watermark 的缓存 output
  → 应用剩余 output
  → synced

sourceText
  → hook/sanitize
  → 空正文：停止，不发送孤立回车
  → final data（含可选 \r）
  → localStorage pending(id, sessionId, data)
  → WebSocket input action
  → PTY write
  → session Map(id,data)
  → input-accepted(id)
```

关键不变式是：`synced` 只能由当前 epoch 的完整 snapshot 产生；pending 必须先落本地再发；accepted 必须在 PTY write 成功且去重记录写入后发送。

### Error and Rescue Registry

| 失败点 | 用户看到什么 | 保留什么 | 自动恢复 | 手动出口 |
|---|---|---|---|---|
| socket close/error | 立即显示断线/旧画面 | terminal、draft、pending | 可见时退避重连 | 立即重试 |
| 10 秒无 snapshot | 同步失败 | draft、pending | 关闭旧 socket 后重连 | 立即重试 |
| 15 秒无匹配 pong | 连接失活 | draft、pending | 重连并重新 snapshot | 立即重试 |
| 连续 3 次同步前失败 | 可能需重新认证 | draft、pending | 仍每 15 秒尝试 | 重新认证并刷新 |
| snapshot 缺新字段 | 服务端版本不匹配 | draft、pending | 不盲目提交 | 刷新/完成部署 |
| localStorage JSON 损坏 | 草稿恢复失败 | 原始坏值不覆盖 | 无 | 用户清空 |
| localStorage 写失败 | 草稿未受保护 | textarea 内当前文本 | 后续编辑继续尝试 | 复制文本后处理存储 |
| sanitize 后为空 | 没有可发送的文本 | draft | 无 | 继续编辑 |
| action 15 秒无响应 | 结果未知 | pending、draft | 同 session 新 epoch 最多一次 | 同 ID 重试/放弃 |
| action rejected | 未接收 + 固定原因 | pending、draft | 仅 write 失败允许原 ID 手动重试 | 放弃或修正后新建 |
| 新 snapshot 的 sessionId 改变 | 上次结果未知 | pending、draft | 禁止自动重送 | 根据屏幕上下文重试/放弃 |
| 无可靠 ID 的畸形消息 | 连接协议错误 | 已落本地内容 | 重连 | 刷新并检查版本 |

所有错误都 fail-loud；不记录语音指令正文，不做静默 catch。

### Failure Modes Registry

| 组合 | 防线 | 验证 |
|---|---|---|
| 旧 socket 的迟到 snapshot/pong | epoch 守卫 | fake timers 单测 |
| snapshot 与 output 交错 | seq + outputWatermark | producer payload 集成测试 |
| PTY 已写、accepted 丢失 | 同 ID 去重并重发 accepted | 断点集成测试 |
| accepted 到达前用户改了 draft | 只清 pending，不清已变化 draft | composer 单测 |
| 发送前页面关闭 | 先持久化 pending | 重载恢复测试 |
| 断线时普通按键被旧队列重放 | 非 synced 禁发且不排队 | e2e |
| autoEnter 被拆成两次写入 | `data` 内含一次回车 | 协议测试 |

### Review by Dimension

1. **架构：** 保留现有单进程边界；不新增连接平台、持久化服务或协议版本系统。回滚只用 snapshot 必需字段守卫。
2. **错误处理：** 连接、snapshot、存储、协议、PTY write 和确认超时均有可见状态与恢复出口；不做静默 fallback。
3. **安全：** Cloudflare Access 和同源边界不变。协议继续校验类型与大小；localStorage 不加无意义的本地加密；日志禁止写入指令正文。
4. **数据与 UX：** 先持久化后发送，发送后仍可编辑；清洗后为空不发孤立回车；关闭 composer 不删除 pending。
5. **代码质量：** 状态留在现有模块。只有为了测试状态转移且确有第二处使用时才抽 helper；不创建 `ConnectionManager`、outbox 或仓储层。

8. **可观测性：** 仅保留浏览器结构化事件 `connection_state`、`snapshot_applied`、`composer_action_state`；服务端只记 id、sessionId、reason，不记 data。无需 dashboard 或告警。
9. **部署：** 无数据库迁移和 feature flag。先部署兼容旧 input 的服务端，再刷新手机客户端；冒烟覆盖旧 input、新 action ack、watermark 和重连。

11. **设计：** 终端继续是主界面；新鲜度用小型状态层，action 状态靠近发送按钮；文字/图标不能只靠颜色，状态更新用 `aria-live`。不新增页面或导航；缩减模式下无需另开视觉设计评审。

### Performance Verdict

- localStorage 同步写入会阻塞主线程，但单条 action 受现有 256 KiB 上限约束，个人长文本场景优先保证每次编辑可恢复，不引入 IndexedDB 或延迟落盘。
- heartbeat 同一时间只有一个小 JSON 帧，约每 10 秒一次，无需性能指标。
- 服务端去重 Map 固定 128 条；不做数据库、TTL worker 或 hash 存储。
- 唯一需新增的资源守卫是 snapshot 前 1 MiB output buffer 上限，防止持续刷屏导致移动端崩溃。
